# Image generation

**Feature id:** `mcp-tools-image-gen` (trace scope) · **Owning feature string:**
`image-gen` · **Dashboard:** `/tools`, results on `/vision` · **Priority 12**

One MCP tool, `image_generate`: draw an image from a text prompt and send it to the
chat.

## The out-of-band delivery contract

This is the interesting part. The generated bytes deliberately do **not** travel in
the tool result. They are handed to the turn's `collectImage` sink
(`server/mcp/context.ts`) and the pipeline delivers them after the text reply.

So the model gets only a **text acknowledgement** — it never sees the image it asked
for. Which is exactly why the result text forbids describing the contents: the model
has no evidence of what was drawn, and a made-up description would be a
hallucination presented next to a real picture.

`features/image-gen/format.ts` shapes that text, and it has to be unambiguous in
both directions:

| Outcome | The model is told |
| --- | --- |
| Success | The image is **already in the chat** and must not be described |
| Failure | **Nothing was sent** and it must not pretend otherwise |

Images are delivered **after** the text reply, so the acknowledgement arrives before
the picture it acknowledges.

## Delivery and recognition

The pipeline delivers the collected images after the reply through the owning
source's outbound port (`server/turn/source-outbound.ts` — the transport's
`POST /internal/chats/:chatId/photos`, or the web chat's in-process port). Each
delivered photo becomes the same pair of rows an incoming media message
produces (user decision, 2026-07-17):

- a media-only `source_messages` **assistant** row — the picture *is* the
  message — mirrored by the ingest from the transport's `message.delivered`
  report, which carries the image bytes;
- a `pending` `source_media` row beside it, hinted as generated by the bot.

In the web chat the pair is a `web_messages` row with pending `web_media`.

Recognition then happens on the normal [vision](vision.md) path. That is what lets a
later turn know what the bot drew, instead of finding a hole in the transcript.

## The tool

| Input | Notes |
| --- | --- |
| `prompt` | 1–2000 chars. Detailed visual description; English works best |
| `size` | Optional `[width, height]`, each 64–4096. Defaults to `[1024, 1024]` |

The description tells the model: only call when the user explicitly asks to
generate/create/draw/paint/make an image; never for casual chat; never to show
something that **already exists** (a photo someone sent, a page it read) — this
draws a new picture, it does not fetch or reproduce existing ones. And it must expand
the user's short request into a detailed, self-contained prompt (subject, setting,
style, lighting, composition), because a one-line request is rarely a good prompt.

## Never throws

`runImageGeneration` resolves an `ok: false` outcome for a provider failure, a
missing configuration, or an empty prompt. A thrown error would abort the whole reply
over a picture the user asked for in passing; instead the model can say "I couldn't
draw that" and carry on.

## Provider details

`server/llm/images.ts` calls `/v1/images/generations` and always requests
`b64_json`: Ollama's image endpoint and the GPT image models return no URLs, so
there is nothing else to ask for.

## Configuration

| Setting | Effect |
| --- | --- |
| `imageBackendId` | The backend row (URL + key) the image endpoint lives on; null reuses the chat backend — a diffusion model rarely lives beside the LLM, hence the separate role |
| `imageModel` | **Null disables the tool** — it returns a clear error result rather than a silent no-op |

Read at call time (`getImageRuntime`), so a settings change takes effect
immediately. The Settings probe (`POST /api/settings/test-images`) generates a
picture and shows it ([Settings](settings.md)).

## Tracing

Every call is its own trace under `mcp-tools-image-gen`, plus the inline
`external_call` event on the reply trace. The generated bytes are not in the trace —
they are in `source_media` (or `web_media`) and rendered on `/vision`.
